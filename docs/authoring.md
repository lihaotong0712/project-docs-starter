# 文档写作与维护

本文供开发者与 AI Agent 共同使用，说明何时写、写什么以及如何维护。先确定本次需要记录的内容，再选择模板；无需在每次工作中创建完整文档集。

## 选择内容与位置

| 分类 | 最少写清楚 | 何时需要 |
| --- | --- | --- |
| design | 目标与范围、核心方案及原因 | 建立项目整体认识，或解释有必要保留的实现机制 |
| spec | 行为规则、适用条件、可判定的验收场景 | 新增或改变需要长期维护的功能、接口或业务规则 |
| development | 目标、待确定问题或任务、完成条件与实际结果 | 工作需要探索、分步执行或跨会话交接 |
| guide | 操作目标、前置条件、步骤与结果检查 | 操作需要被其他人或后续会话重复执行 |
| adr | 决策背景、选择、重要备选方案与后果 | 重要取舍需要独立追溯时，可选 |

- 业务目标和总体范围放在设计概览，精确业务规则放在规格中。
- 设计说明机制与理由，规格定义可观察行为。
- 局部设计很短时可以作为规格的一节；跨功能架构放 design。
- 调研结论、原型反馈和验证证据优先放在对应开发记录中，确认后的规则和方案更新到规格与设计。

每条规则只维护一份完整定义，其他位置链接引用。已有 schema、API 定义或可执行场景时，说明其覆盖范围并引用，不复制维护。普通修正可以仅使用 Issue 或 PR，不强制新建开发记录或 ADR。

## 从零开始与后续迭代

先把概念性需求写成“谁在什么情况下遇到什么问题，希望得到什么结果”，再逐步确定范围、行为和实现方案。需求可以在设计概览或功能规格中表达，无需独立目录。

| 阶段 | 起点与共同活动 | 写入何处 | 继续工作的条件 |
| --- | --- | --- | --- |
| 明确目标 | 开发者提供问题、价值和限制，Agent 追问歧义并整理范围 | design 概览，简单功能可直接写 spec 背景 | 目标、首批范围与非目标足以安排探索 |
| 调研与原型 | 检查现有实现、比较方案，必要时用最小原型验证体验或验证可行性 | development 中的问题、来源、原型、反馈与结论 | 影响下一步的重要不确定性有结论，或明确缩小范围 |
| 设计与行为讨论 | 共同讨论机制、正常例子、边界和失败例子，确认重要取舍 | design 与 spec，必要时 ADR | 当前开发范围的规则与方案足以指导实现和验收 |
| 计划与验收准备 | 按能力分任务，明确依赖、测试和完成条件 | development 引用规格场景 | 可开始的任务和验证方法明确，所需授权已具备 |
| 实施与验证 | 编码、测试、审查，发现歧义时返回讨论 | 代码与测试，development 记录进度和证据 | 适用检查完成，失败与未验证范围明确 |
| 部署与交付 | 按目标环境验收，更新长期文档和操作方法 | guide、design、spec 及开发记录收尾 | 交付范围与结果对应，剩余限制可见 |

### 开发者与 Agent 如何协作

开发者提供领域事实、价值判断与反馈，按项目授权确认重要范围、行为、验收条件和方案取舍。Agent 调查已有代码和资料、整理问题与候选方案、起草文档，并在授权范围内实现和验证。双方共同用具体例子澄清歧义。

确认应留下可定位的依据，例如 Issue、PR 审阅或实际讨论记录。已有明确决定或执行授权时沿用，不为每篇文档增加重复审批。Agent 不允许把自己的建议当作批准，也不允许虚构确认人、日期或记录。

会话结束或交接时，在开发记录中维护当前任务、已完成证据、阻塞与下一步，注明相关文件和必要环境。下一位参与者先读项目规则、相关规格和当前开发记录，再按需要读设计与指南，无需遍历全部文档。

持续适用的协作偏好按项目规则维护，Agent 需要始终遵守的规则由 `AGENTS.md` (或 `CLAUDE.md`) 记录或链接。临时纠正只作用于当前工作，需要长期保留时形成规则，如果难以根据上下文判断，Agent 应询问用户。

### 几种开发思路如何体现在写作中

| 思路 | 在文档中落实的动作 | 需要避免的误解 |
| --- | --- | --- |
| FDD：功能驱动开发 | 按使用者价值列出功能，选择可独立交付、验证的范围 | 提出概念需求只是起点；环境准备等支撑任务可以独立存在 |
| PDD：原型驱动开发 | 明确假设，制作原型，获取实际反馈并调整范围或方案 | 只查资料不算原型验证，原型能演示不等于正式能力完成 |
| BDD：行为驱动开发 | 共同发现规则，用正常、边界和反例澄清，整理验收场景 | 只填写“假如、当、那么”句式无法替代共同讨论 |
| SDD：规格驱动开发 | 先形成当前范围可实现、可验证的规格，再指导实现并随变化维护 | 不要求一次写完整个项目，也不把设计固定排在规格之前 |
| ATDD：验收测试驱动开发 | 实现前根据已确认场景准备验收测试，用结果反馈开发 | 实现后补测应如实记录为补充验证；环境故障与行为失败需区分 |

这些是对上述方法部分实践的借鉴，不要求完整采用某个框架或工具。规格、设计、任务与测试通过链接对应，需要多处引用时再为规则或场景分配稳定编号。

### 初始开发、迭代与小修正

初始开发先形成项目目标、系统边界、首批功能及必要支撑任务，再逐项细化。后续迭代复用当前设计和规格，在开发记录中明确现有行为、本次变化、保留范围、兼容与迁移影响。

缺陷修复可以直接引用已有规则并补回归场景。小修正使用 Issue 或 PR 即可，当探索或交接需要时再建立开发记录。

## 各类内容怎么写

### 设计内容的写法

同一份设计可以包含多种内容，但各节解决的问题应明确。总体设计优先写在 [design/README](design/README.md) 中，具体专题需要展开时再建立专题文件。

| 内容 | 要回答的问题 | 合适的表达与边界 |
| --- | --- | --- |
| concept：概念解释 | 为什么需要这个概念，与其他概念有什么关系？ | 准确术语、状态和规则引用规格，用贯穿例子解释 |
| architecture：架构 | 系统边界是什么，模块如何分工与协作？ | 上下文、模块、运行或部署视图按需选择，说明依赖和数据归属 |
| business：业务目标与流程 | 谁在什么场景做什么，系统如何支持？ | 描述参与者、触发、流程与结果，精确业务规则在 spec 定义 |
| feature：功能设计 | 这项能力通过什么机制实现，为什么这样做？ | 说明核心方案、关键交互、资源生命周期等 |

推荐使用 mermaid flowchart 等图表展示业务流程。
图表用于解释关系，文档仍需写清关键条件与取舍列表。
质量要求应有适用条件和判定标准，设计解释满足要求的机制。
已知风险与技术债记录影响、后续处理条件和跟踪入口。

### 规格、场景与验收测试的写法

先写规则，再通过例子发现遗漏。例如“任务完成后可以下载结果”仍需讨论谁能下载、未完成时会发生什么、结果过期后如何反馈。确认后的规则描述可观察结果，内部队列或存储方案放设计。

场景写明初始条件、动作、结果及必要副作用，覆盖实际适用的正常、边界、失败和反例。表格与“假如、当、那么”二选一即可。可执行场景或机器可读定义已经覆盖的内容明确权威位置，Markdown 只链接并解释必要背景。

开发记录引用场景安排测试，说明测试层次、位置、环境和初始结果。测试实现应检查真实行为及重要边界，不只复述实现。无法自动化时写清人工步骤与成功判据，实际执行结果记录证据。

### 调研、原型与任务的写法

调研从影响决定的问题出发，选择足以回答问题的来源或实验。记录版本、条件与限制，将来源事实、观察和推断分开。证据不足时给出待验证假设及下一步，不将推荐方案写成确定结论。

原型选择最小的验证范围，保留产物入口、复现方法、演示或模拟部分以及实际反馈。结论要说明采纳、调整、放弃或继续验证了什么，并更新对应设计或规格。原型代码转正式实现前，明确还缺哪些生产要求与验证。

任务按可交付能力分组，列出依赖、修改对象和可检查的结果。例如“完成导出功能”应拆成可验证的行为，而“实现任务状态查询，使未完成任务返回规定状态，并运行对应场景测试”可以直接判断结果。具体粒度以便于实施和验证为准，不按每个文件机械拆任务。

### 按阅读目的组织内容

| 目的 | 写法 | 默认位置 |
| --- | --- | --- |
| 学习 | 固定的小练习、逐步反馈、最终成果与清理 | guide，采用模板中的教程提示 |
| 完成任务 | 目标、条件、步骤、结果检查和失败处理 | guide |
| 查询 | 精确、结构一致的条目，便于定位参数和规则 | spec，优先引用机器可读定义 |
| 理解 | 背景、概念关系、机制与取舍 | design |

较长的概念解释和参数表通过链接提供，避免夹在操作步骤中打断执行；简单必要背景可以直接保留在步骤旁。

## 聚合与拆分

同一主题经常一起阅读的背景、规则、场景和必要设计可以放在一篇文档，用章节区分。内容具有独立读者、更新节奏或复用需求时再拆分，不必按篇幅机械拆分。

普通文件使用 `kebab-case.md`。分类内先直接放主题文件，需要分组时再建立主题目录，以其中的 README 作为入口。模板统一命名为 `TEMPLATE.md`，各主题复用分类模板，不复制整套目录。

总入口链接分类，分类入口维护主题索引，子目录自行维护所属主题，避免多处重复列表。移动或删除文档时同步修正出入链接。截图、原型和实验脚本按需放在相邻的同名主题目录中，正文说明用途和执行方法。

## 文档状态与生命周期

`docs/` 中的 Markdown 文件使用以下元信息。普通文件填写实际日期，模板允许占位日期。

```yaml
---
type: design
status: Draft
updated: YYYY-MM-DD
---
```

`type` 使用非空字符串。`docs/README.md`（文件名大小写均可）必须使用 `index`，`docs/<subject>/*.md` 必须使用所在分类名；嵌套文档可以使用一级分类名或直接父目录名，不匹配时只警告。其他根级文件没有类型匹配规则，只警告，例如本文使用 `index`。分类名无需在检查器中登记。

`updated` 是实质内容更新日期，不表示重新验证。关联资料与适用版本在正文说明。

以下状态表达文档的审阅、采纳、退出与历史保留情况。各类文档选用适合的状态，不要求依次经过全部状态。

| 状态 | 含义 | 后续处理 |
| --- | --- | --- |
| Draft | 正在起草，内容可能不完整 | 补充内容与待确认问题，准备好后进入 InReview |
| InReview | 当前版本已准备好，等待审阅或决定 | 根据反馈返回 Draft，或确认、否决 |
| Accepted | 内容已确认，适用于声明的范围 | 持续维护，明确适用版本；不表示已经实现或通过验证 |
| Rejected | 提案经过讨论后未被采纳 | 有追溯价值时保留原因，否则删除并修正引用 |
| Deprecated | 已不建议继续采用，现有使用可能仍受支持 | 说明退出条件、支持范围和替代方案；没有替代项时明确说明 |
| Superseded | 已被其他文档或决策替代 | 说明替代范围并链接替代项，保留必要历史 |
| Archived | 已结束维护，仅供历史查阅 | 说明归档原因；存在当前资料时提供入口，否则说明没有后续项 |

Rejected 表示内容未被采纳，工作取消则可能源于优先级或资源变化，不能仅因工作取消就否决文档。Deprecated 表达退出过程，Superseded 表达明确的替代关系；完全失效且没有替代项的历史文档可以 Archived，普通无保留价值的内容可以删除。

### 各类文档如何选择状态

| 文档 | 常见变化 | 使用说明 |
| --- | --- | --- |
| 设计、规格 | Draft → InReview → Accepted，后续按需 Deprecated 或 Superseded | 否决的提案使用 Rejected，仅供历史查阅的资料可以 Archived |
| 开发记录 | Draft → InReview → Accepted，结束维护后按需 Archived | 工作进度与文档状态分别记录，完成工作不强制归档 |
| 指南 | Draft → InReview → Accepted，后续修订、弃用或替代 | 确认前按适用环境验证步骤，无法验证的范围明确说明 |
| ADR | Draft → InReview → Accepted 或 Rejected，已采纳决定可被 Superseded | 仅退出但尚无替代决定时可以 Deprecated，保留原始理由 |

审阅可以在现有讨论或 PR 中完成，不要求独立审批阶段。简单修改可以直接从 Draft 确认为 Accepted；InReview 收到需要实质修改的反馈后返回 Draft，再次准备好时重新进入审阅。

文档确认、工作进度与验证结果分别表达。开发记录正文使用“待开始、进行中、已完成、已取消”描述整体进度，以任务列表记录具体工作，以验证章节记录实际结果，不增加另一套 frontmatter 状态。暂停时保留当前进度并说明暂停原因与恢复条件。

已确认文档中的实质性拟议修改，在确认前使用 Draft 或 InReview，并明确现行规则与拟议变化，或在开发记录中起草并链接当前文档。不得让 Agent 将尚未确认的提案视为现行要求。确认依据可以是 PR 审阅、Issue 或其他可定位的决定，不要求额外审批系统。

开发完成时先更新 design、spec 和 guide，再按追溯价值保留或删除工作记录；仅供历史查阅时改为 Archived，并说明结束维护的原因。已完成功能尚未验证时，应明确写出未验证范围；勾选任务需有完成依据。

普通过时文档可以删除并修正引用，历史内容由 Git 保留。ADR 采纳后保留原始背景与理由，后续决策通过新记录替代，旧记录标记 Superseded 并互相链接。

### 状态变化时具体更新什么

| 事件 | 文档动作 | 需要保留的依据 |
| --- | --- | --- |
| 新建提案 | 使用 Draft，写明范围与待确认事项 | 来源、假设或需要讨论的问题 |
| 提交审阅 | 准备好的版本改为 InReview，明确审阅范围与待决定问题 | 实际审阅入口 |
| 提案被否决 | 按需使用 Rejected 并保留原因，或删除并修正引用 | 实际决定及未采纳原因 |
| 方案或规则确认 | 更新相关章节和场景，确认整篇内容后改为 Accepted | 实际确认记录及适用范围 |
| 修改已确认规则 | 小变更可在原文起草并区分现行与拟议内容；复杂变更先在开发记录起草 | 当前基线、变化原因、影响与确认依据 |
| 实现完成 | 更新开发任务进度，标明适用版本或实现入口 | 修改记录，不以实现完成替代测试结果 |
| 验证结束 | 记录通过、失败或未执行，以及范围与环境 | 实际命令、测试或人工结果 |
| 取消或结束工作 | 更新最终设计、规格和指南，处理原型与临时产物 | 结果、剩余限制与必要追溯记录 |
| 不再建议采用 | 使用 Deprecated，说明退出条件与现有支持范围 | 弃用原因与替代方案（如有） |
| 文档或决策被替代 | 使用 Superseded，明确替代范围并互相链接 | 新旧资料的替代关系 |
| 结束维护 | 有历史价值时使用 Archived，否则删除并修正引用 | 结束维护的原因与当前资料入口（如有） |

已确认规格可能描述尚待实现的目标，正文需明确适用情况，例如“本文为下一版本的已确认要求，当前实现进度见开发记录”。已有发布版本与下一版本并存时明确各自范围，不让读者从 Accepted 推断已发布。

一篇文档包含已确认和待确认内容时，frontmatter 表示整篇文档的生命周期状态。重要未决修改使整体使用 Draft 或 InReview，正文标出仍有效的基线；如果会妨碍查询当前规则，保持长期文档不变，在开发记录中起草变更。单纯校对不撤销已有确认。

## 事实与表达

结论须有可定位的来源或实际结果，区分事实、推断和待确认内容。改写保留适用条件、例外、风险和确定程度；命令、路径、字段名和固定引用只有在存在技术依据时才修改。发现文档与实现冲突时，核对适用版本及确认依据，再修正对应内容。

- 使用直接、准确的中文，说明具体对象、动作和结果，避免空泛修饰和含义不明的术语；指代不清时写出对象名称。
- 直接描述当前行为或结果，减少“是……不是……”“完成了……而不是……”等重复的正反表述。仅在区分易混概念、说明重要边界或防止误操作时保留对比和否定。
- 一个段落围绕一个主要信息点，一个句子保持清晰的主干；标题反映用途，列表项保持相同层级和句式。删除重复信息时保留必要的条件和例外。
- 同一概念使用同一首选术语，优先沿用项目术语及产品官方写法；首次出现的专有术语和缩写按读者需要解释，共享定义通过链接引用。
- 按实际含义使用“要求”“规范”“决策”“决定”“约束”或“建议”。仅在明确的交互双方需要共同遵守接口、协议等约定时使用“契约”（contract），避免将一般要求提升为契约。
- 中文正文在源文件中保持一段一行，使用编辑器软换行阅读；保留代码块、表格、引用和显式换行的结构。批量调整前先识别并保护代码、链接及其他机器可读内容，调整后人工复核。

## 检查与维护

行为改变时更新规格与验收场景，机制改变时更新设计，操作改变时更新指南；重要选择按需记录 ADR。核对默认值、示例、机器可读定义与正文是否一致，并说明省略值、覆盖和生效规则。

在仓库根目录运行以下检查，依赖与检查范围见仓库中的 `.github/check-docs/README.md`。

```sh
npx -y markdownlint-cli2@latest
node .github/check-docs/check-docs.mjs
```

提交前检查格式、元信息和本地链接，并人工复核事实、条件和步骤。实际命令、环境、结果及未执行原因记录在 PR 或开发记录中；自动检查不证明内容正确或实现完成。
