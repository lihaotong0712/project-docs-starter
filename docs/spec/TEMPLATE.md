# 功能或模块规格

至少保留范围、可观察行为和验收场景，其他章节按实际需要裁剪。简单功能可以合并章节；模块规格应说明覆盖的功能与使用方。规格写预期规则，执行结果放开发记录。

## 背景、范围与适用情况

说明使用者、要解决的问题、功能目标、适用版本与不覆盖的范围。链接总体设计或已有需求，不要求另建需求文档。标明本文描述当前规则还是拟议变化，注明实现情况的查询入口。

## 术语与规则

定义必要术语、标识符、单位、时间和编码约定。共享定义只链接引用。使用“必须”“不得”“可以”时明确适用对象与条件，业务规则说明触发条件和可观察结果。

## 可观察行为

按用户目标或公开入口，说明前置条件、调用者权限、输入、结果、副作用和成功后的状态。异步行为区分受理与完成，说明结果如何查询及完成判据。

界面按实际需要区分加载中、没有数据、无权限和加载失败等状态，说明反馈与危险操作的影响。库、CLI 或协议按自身公开入口描述，不套用服务端接口格式。

## 接口、数据与配置

涉及结构化输入、输出或持久化记录时，说明类型、必填性、取值范围、单位、唯一性、字段间约束和非法值处理。区分省略、空值与零值，定义未知字段的处理。

已有 schema、配置或 API 定义时，明确其权威范围并引用。默认值标明定义位置，说明省略、覆盖顺序和生效时机；示例值与环境覆盖值单独标注，不重复维护完整字段表。

## 状态、时序与并发

定义可观察状态、合法转换、转换条件和禁止操作。存在超时、顺序、重复调用、幂等或并发要求时，说明计时起点、请求身份和保证范围。

区分传输状态、业务状态与界面反馈。完整协作过程链接设计，不用内部实现步骤代替外部行为要求。

## 失败与重试

说明失败条件、可观察错误、操作是否生效及状态如何保留。结果未知时说明如何查询或安全恢复；需要重试时写清允许条件及重复操作的结果。

错误说明应帮助使用者识别问题和采取行动。恢复机制链接设计，具体操作链接指南。

## 质量要求与兼容性

用具体条件和可判定标准描述相关质量要求，指标需有依据。说明支持环境、接口和数据兼容范围，以及字段或语义变化对现有使用方的影响。

存在迁移时说明迁移前后的行为、保留的数据和弃用条件，操作步骤链接指南。没有存量使用方时不添加推测性的兼容路径。

## 行为场景与验收

先共同讨论规则的具体例子，再整理场景。覆盖适用的正常、边界、失败、反例和重要状态变化；场景必须能判断结果。可选择表格或以下句式，无需重复表达。

```text
场景：具体业务行为
  假如 已知初始状态
  当 使用者或外部系统触发动作
  那么 出现可观察的结果
  并且 产生明确副作用，或保持指定状态
```

| 场景 | 前置条件 | 输入或操作 | 预期结果与副作用 |
| --- | --- | --- | --- |
| 填写具体场景 | 初始条件 | 触发行为 | 可判定结果 |

需要跨文档引用时设置稳定编号。采用可执行场景时链接其权威文件，不在 Markdown 维护副本。开发记录引用这些场景安排实现前的验收测试，并记录执行条件与结果。

## 必要设计与关联资料

简短局部设计可以写在这里，跨功能机制链接 design。链接已有测试、机器可读定义、指南与重要决策，说明各自覆盖范围。

## 待确认事项与确认依据

列出存在歧义的规则、影响范围和需要决定的问题。确认后修改相关行为与场景并记录依据，不将未决内容作为当前承诺。
